# CyberCity — Vision

## Что такое CyberCity?

CyberCity — это **цифровой двойник городской ИТ/ОТ-инфраструктуры**, созданный
как платформа для обучения кибербезопасности, исследований и публичной
демонстрации.

Город моделируется как ориентированный граф:

- **Организации** представляют реальные сущности: банки, больницы,
  энергетические компании, правительственные учреждения, школы, телекомы.
- **Сервисы** — узлы графа: веб-порталы, базы данных, SCADA-шлюзы, DNS,
  бэкапы, рабочие станции.
- **Связи** — рёбра: потоки аутентификации, API-вызовы, чтение БД,
  резервные копии, vendor VPN.

Цель — не очередная уязвимая CTF-машинка, а **живой, наблюдаемый, объяснимый
город**, где инциденты безопасности распространяются через зависимости, где
игроки могут прослеживать пути атак, а каждое изменение состояния имеет
записанную причину.

## Зачем существует этот проект

1. **Публичный след для senior-инженера.** Проект демонстрирует архитектуру,
   распределённые системы, platform engineering, знание домена
   кибербезопасности и операционную дисциплину в единой целостной системе.
2. **Reference implementation event-driven digital twin.** Многие
   security-платформы нуждаются в causal provenance, replay и graph-based
   propagation. CyberCity исследует эти идеи в конкретной, тестируемой форме.
3. **Площадка для hybrid cyber ranges.** Соединяет лёгкие stub-контейнеры и
   настоящие VM/контейнеры через общий event bus — от маленького старта
   до полноценного полигона.

## Принципы

### Data as code

Город декларируется в YAML в `cybercity-data`. Он версионируется,
валидируется и рендерится в артефакты. Runtime потребляет эти артефакты,
никогда не хардкодит топологию.

### События — единственный источник истины

Runtime-состояние — проекция потока событий. Если известны все события,
можно восстановить всю историю города. Это даёт аудит и compliance, replay
и what-if анализ, объяснимые переходы состояний, отладку и разбор сценариев.

### Два графа, один runtime

- **Топологический граф** отвечает: *что с чем связано?*
- **Событийный граф** отвечает: *что произошло и почему?*

Они разделены, но связаны. Топология — это рельсы; события — поезда на этих
рельсах.

### Engine — единственный мутатор

Только `cybercity-engine` изменяет состояние мира. UI, автор сценариев,
коллектор и реальные сервисы шлют события; движок валидирует и применяет. Эта
граница упрощает консистентность и делает систему наблюдаемой.

### Hybrid by design

У сервиса есть **runtime_kind** (deployment-time) — как он исполняется:

- **vm** — полная VM с настоящей ОС/ПО;
- **container** — контейнер с настоящим ПО (gVisor/Kata для изоляции);
- **lite** — лёгкий stub-контейнер с реальным сокетом + подделанным баннером
  (массовый фон города).

И отдельно — флаг **honeypot** (назначение-наживка, ортогонален `runtime_kind`):
специально привлекательная фейковая цель для сбора threat intel.

Движок — регистратор, не симулятор: все runtime-цели наблюдаются
`cybercity-collector` out-of-band единообразно, исход приходит как подписанное
событие. Никаких «выдуманных движком» сервисов. Обоснование —
[`adr/0004-runtime-kind-vm-container-lite.md`](adr/0004-runtime-kind-vm-container-lite.md).

### Безопасность по умолчанию

- Сетевая сегментация явная.
- Секреты и учётные данные никогда не коммитятся.
- Публичный доступ только read-only и через туннель.
- OT/ICS-сегменты изолированы от management и публичных сетей.
- Наблюдение за гостями — только out-of-band, с подписанными событиями;
  in-guest телеметрия — best-effort и **никогда** не источник для scoring.

## Целевые аудитории

| Аудитория | Что она получает |
|-----------|------------------|
| Рекрутеры / hiring managers | Целостная, документированная, протестированная система с чёткой архитектурой и публичной демонстрацией. |
| Security-инженеры | Модель attack surface, propagation, incident response training. |
| Platform-инженеры | Пример event-driven runtime, GitOps, observability, hybrid execution. |
| Студенты / учащиеся | Возможность увидеть, как инфраструктурные зависимости порождают каскадные риски. |
| Будущие контрибьюторы | Чёткие ADR, границы и точки расширения. |

## Критерии успеха

Проект считается успешным, когда:

1. Посетитель может открыть публичный URL и увидеть живой интерактивный граф
   города.
2. Игрок может вызвать событие и наблюдать, как оно распространяется через
   зависимости.
3. Каждое изменение состояния города объяснимо через событийный граф.
4. Каждый репозиторий имеет чёткую архитектуру, ADR, тесты и CI.
5. Система работает на home lab и концептуально масштабируется до production
   cyber range.

## Non-goals

- Полная физическая реалистичность воды, электричества или транспорта.
- Замена коммерческим cyber-range платформам.
- Реалистичная эмуляция трафика масштаба ISP.
- 3D-визуализация уровня игрового движка.

## Где что лежит

| Репозиторий | Роль |
|-------------|------|
| `cybercity` | **Этот репозиторий** — обложка; системное видение, архитектура, конвенции, сквозные ADR. |
| `cybercity-data` | Каноническая декларативная модель города, валидатор, билдер, автор сценариев. |
| `cybercity-engine` | Event-driven runtime: два графа, tick-loop, replay, scoring. |
| `cybercity-manage` | Контрольная плоскость: provisioning, reset/rollback, изоляция, квоты; размещает коллектор. |
| `cybercity-collector` | Внешний out-of-band per-host коллектор; подписанные события в engine по Kafka. |
| `cybercity-ui` | Web-фронтенд: карта, таймлайн, дашборды, отчёты. |

> Единый источник правды о составе и контрактах — [`COMPOSITION.md`](COMPOSITION.md).
> Как реализовано в каждом репозитории — в его собственном `AGENTS.md` и `docs/`.
