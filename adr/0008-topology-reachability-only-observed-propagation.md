# ADR-0008: топологический граф — только достижимость; пропагация наблюдается, не вычисляется

## Status

Accepted

## Scope

Сквозное.

## Context

До сих пор топологический граф моделировался типизированными рёбрами
(`api-call`, `auth`, `db-read`, `backup-of`, `same_org`, `exposure_chain`, …),
а движок **вычислял** пропагацию исходов по этим рёбрам (см.
[`../DATA_FLOW.md`](../DATA_FLOW.md) § «Жизненный цикл события», шаг Propagation;
[`../ARCHITECTURE.md`](../ARCHITECTURE.md) § «Два графа»). Три проблемы:

1. **Ненаблюдаемость.** Коллектор out-of-band видит сокеты, соединения, состояние
   хоста (fs/net/mem/proc) — но не «креда `svc_db` использована для auth в B»
   (это in-guest, часто под TLS; у `lite` кредов нет вообще). Семантическое ребро
   нельзя *наблюдать* — только *декларировать*. По
   [ADR-0002](0002-trust-boundary.md) декларативное/ненаблюдаемое — не авторитетно
   для scoring.
2. **Конфликт с ADR-0004.** Движок, выводящий «B скомпрометирован» из ребра
   `auth` A→B *до того*, как коллектор это увидел, — это движок-симулятор; прямой
   конфликт с «движок — регистратор, не симулятор»
   ([ADR-0004](0004-runtime-kind-vm-container-lite.md) §2).
3. **Дублирование.** Kill-chain уже смоделирован на уровне **vuln** через
   `requires`-DAG ([ADR-0006](0006-vulnerability-declarative-overlay-realism.md)),
   не на уровне сервис-графа. Типизированные рёбра сервис-графа для scoring
   не load-bearing.

## Decision

### 1. Топологический граф — нетипизированная достижимость

Ребро «A достижимо из B» **без вида**. Наличие ребра выводится из: общей сети
(`same_network` → reachable), объявленной экспозиции (`exposure` → publicly
reachable), Multus per-service IP. Никаких `api-call` / `auth` / `db-read` /
`backup-of` / `same_org` / `exposure_chain` как **типов** рёбер — `same_network`
и `exposure` становятся *способом вывести наличие ребра*, а не его типом.

### 2. Пропагация наблюдается, не вычисляется

Движок **не выводит** «B пало» из графа. Коллектор наблюдает состояние каждого
сервиса out-of-band; при смене состояния (compromised и т.п.) шлёт подписанное
событие; движок записывает. Атака расползается по карте ровно потому, что
коллектор *видит*, как игрок реально движется по рёбрам достижимости, и
сообщает каждое падение. Движок = чистый регистратор — это завершение
[ADR-0004](0004-runtime-kind-vm-container-lite.md) §2: пропагация тоже
наблюдается, а не симулируется.

### 3. vuln `requires` — валидатор, не драйвер

`requires` из [ADR-0006](0006-vulnerability-declarative-overlay-realism.md)
меняет роль: из драйвера пропагации → в **валидатор**. Когда коллектор сообщает
«V2 эксплуатируется», движок проверяет по событийному графу, что V1 уже
эксплуатировался; иначе событие невалидно/помечается. `requires` — ограничение
на *наблюдаемые* события, не механизм их предсказания.

### 4. Два графа сохраняются

Топологический (теперь достижимость) + событийный (append-only,
`caused_by` / `propagated_to` / `triggered_rule` / `response_to`). Причинность
**реконструируется** из наблюдённых событий, не вычисляется вперёд. Принцип
«события — единственный источник истины»
([`../VISION.md`](../VISION.md)) — на месте.

## Consequences

### Positive

- Прямое завершение «движок — регистратор»
  ([ADR-0004](0004-runtime-kind-vm-container-lite.md)): класса
  «engine-derived service outcomes» нет, ровно как класса
  «engine-synthesized service events» нет. Доверительная граница
  ([ADR-0002](0002-trust-boundary.md)) проще: все исходы — коллектор-наблюдаемые.
- Честность наблюдаемости: граф содержит только то, что коллектор может
  подтвердить (достижимость = сокеты/сети; состояние = зонды). Нет
  декларативных семантических рёбер, которые нельзя ни проверить, ни
  scoring-авторизовать.
- Меньше движок: уходит подсистема propagation-правил по типам рёбер. Движок =
  consumer-loop + граф достижимости + scoring + валидатор `requires` + API.
- Меньше data: уходит авторинг типизированных рёбер; остаётся сеть/экспозиция +
  vuln-сущности.
- MVP ([ADR-0007](0007-mvp-scope.md)) уже collector-driven; 0008 приводит модель
  графа в соответствие с тем, как MVP реально работает (Cilium = сетевые политики
  = рёбра достижимости).

### Negative

- Нет проактивного «если A падёт, B под угрозой» (предсказание blast radius).
  Движок знает только случившееся, не возможное. Для учебного/демо-полигона —
  приемлемо (учатся на реальных атаках); для «what-if до атаки» — отдельный
  анализ поверх графа достижимости + vuln, не ядро runtime.
- Атака расползается ровно с той скоростью/полнотой, с которой коллектор способен
  её наблюдать. Слабая видимость коллектора = слабая видимость расползания.
  Смягчение: каталог зондов ([ADR-0003](0003-collector-rust-out-of-band.md) /
  [ADR-0007](0007-mvp-scope.md)) покрывает ключевые индикаторы; для `vm`
  memory-introspection — future (ADR-0007 §2).
- Теряется человекочитаемая семантика рёбер на карте (`auth`/`db-read` как
  подписи). Замена: vuln-сущности и их `requires` несут kill-chain-нарратив;
  рёбра достижимости — без подписей.

## Alternatives considered

- **Богатый семантический граф + движок-пропагация (прежнему):** отвергнуто —
  рёбра ненаблюдаемы out-of-band (проблема 1) и делают движок симулятором
  (проблема 2), против ADR-0004.
- **Семантические рёбра как `narrative`-слой (параллельно достижимости), движок
  рассуждает, но scoring не авторитетен:** отвергнуто — плодит второй класс
  исходов (декларативно-выведенные) поверх наблюдаемых, усложняет доверительную
  границу без load-bearing пользы (kill-chain уже в vuln `requires`).
- **Только достижимость, но движок всё же предсказывает blast radius:**
  отложено — это аналитика поверх графа, не ядро runtime; возвращается отдельным
  механизмом, если понадобится.
