# AGENTS.md — хаб CyberCity

Хаб хранит системный контекст программы: `COMPOSITION.md` (состав, границы,
версии), `CONVENTIONS.md` (event envelope и общие контракты), `BACKLOG.md`
(задачи), системный `docker-compose.yml` и `adr/`. Кода сервисов, интерфейсов
и автономных компонентов здесь нет.

Общие полномочия и запреты, рабочий цикл, архитектурный канон и правила поставки —
в закреплённой методологии
[`TheCipherKeeper/addm`](https://github.com/TheCipherKeeper/addm) (далее
`<methodology-repo>`): `<methodology-repo>/AGENTS.md` и
`<methodology-repo>/docs/`. Ниже только локальные правила хаба.

## Авторитет

Порядок приоритета: методология → этот `AGENTS.md` → `COMPOSITION.md` /
`CONVENTIONS.md` / `adr/`. Противоречие внутри одного уровня — дефект. Один факт
хранится в одном месте; остальные документы ссылаются на него, а не пересказывают.

## Задачи

- `BACKLOG.md` — единственный источник истины о задачах: человек ведёт его,
  агент берёт первый `[ ] ready`. Машинная проекция задач не используется,
  `.tasks/` не ведётся.
- Человек создаёт задачу без классификации. Агент до реализации добавляет риск,
  автономность, триггеры и откат отдельным служебным PR `task-qualification`,
  который меняет только `BACKLOG.md`.
- `[x]` ставится только после слияния, развёртывания в тестовой среде, успешных
  проверок и создания `.evidence/TASK-NNNN.json` служебным PR `task-finalization`.
- Заглушка и TODO не считаются реализацией или выполненной задачей.

## Состав и контракты

- Состав репозиториев, их назначение и высокоуровневые границы задаёт человек;
  агент отражает явное решение в `COMPOSITION.md` и не создаёт и не удаляет
  репозитории сам.
- `COMPOSITION.md` — единственный реестр компонентов, версий и связей.
- `CONVENTIONS.md` — только общесистемные контракты; версионируется
  (`CONVENTIONS@vN`). Выпущенная версия `@vN` неизменна; несовместимое изменение —
  `@vN+1` отдельным PR, после чего сервисы мигрируют каждый своим PR.
- Сервисы взаимодействуют только через брокер. Интерфейс обращается к единственному
  сервис-шлюзу по HTTP/WS; автономный компонент наблюдается out-of-band и в брокере
  не участвует.
- Системный `docker-compose.yml` собирает образы компонентов из `COMPOSITION.md`.

## ADR

- ADR хранится в `adr/NNNN-kebab-case.md`; нумерация сквозная, все ADR программы —
  в хабе.
- Обязательные разделы: `Status`, `Scope`, `Context`, `Decision`,
  `Consequences`, `Alternatives considered`, `Related`.
- `Scope` — `Сквозное` или список затронутых репозиториев.
- Допустимые статусы: `Accepted`, `Proposed`, `Superseded`, `Amended`. Старые
  решения помечаются заменёнными, а не удаляются. Индекс — `adr/README.md`,
  шаблон — `adr/_TEMPLATE.md`.

## Нейминг, README и лицензии

- Репозитории называются `cybercity-<slice>`; хаб — `cybercity`.
- Идентификаторы сущностей и топологии — kebab-case.
- README содержит краткую сводку и ссылки на канонические документы, но не

## Проверка и коммиты

Перед коммитом запускается закреплённый verifier методологии
(`uv run <methodology-repo>/tools/verify/verify.py`). Недоступность обязательной
проверки не считается успехом.

Коммиты используют Conventional Commits. Допустимые области:
`composition`, `conventions`, `deploy`, `adr`, `docs`. Документация и тело
коммита — русские; идентификаторы и краткое описание коммита могут быть
английскими. Несовместимость отмечается `BREAKING CHANGE:` в теле.
