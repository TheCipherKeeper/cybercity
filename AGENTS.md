# AGENTS.md — правила работы в хаб-репозитории

Этот репозиторий — хаб CyberCity. Он хранит канонический `BACKLOG.md`, состав
системы и границы репозиториев в `COMPOSITION.md`, общие контракты в
`CONVENTIONS.md`, системный `docker-compose.yml` и архитектурные решения в
`adr/`. Код сервисов здесь не хранится.

Методология:
[`TheCipherKeeper/ai-project-template`](https://github.com/TheCipherKeeper/ai-project-template).
Начальная точка — `docs/START.md`, выполнение задачи — `docs/WORKFLOW.md`,
указатель — `docs/INDEX.md`. Точная версия закреплена в `.methodology.yml`.

## Авторитет

Порядок приоритета: методология → этот `AGENTS.md` → `COMPOSITION.md` /
`CONVENTIONS.md` / `adr/`. Противоречие внутри одного уровня является
дефектом. Один факт хранится в одном месте; остальные документы ссылаются на
него, а не пересказывают.

## Работа с задачами

- Агент выполняет первую задачу `[ ] ready` из `BACKLOG.md`; одновременно
  выполняется одна задача.
- `BACKLOG.md` — единственный источник истины. `.tasks/` синхронизируется
  штатным инструментом методологии и вручную не редактируется.
- Агент самостоятельно определяет технический план, тесты, риск и откат, но не
  придумывает отсутствующий продуктовый замысел и не меняет заданные человеком
  репозитории или их назначение.
- Обычная функциональность проходит независимую проверку; специальные проверки
  включаются триггерами из `docs/REFERENCE.md`.
- `[x]` ставится только после слияния, тестового развёртывания, успешных
  проверок и создания `.evidence/TASK-NNNN.json`.
- Заглушка и TODO не считаются реализацией или выполненной задачей.

## Git и публикация

- `main` — единственная интеграционная ветка.
- Работа ведётся в `feat/TASK-NNNN-<slug>` и попадает в `main` только через PR.
- Прямой коммит в `main`, ветки `dev` и release-ветки запрещены.
- После успешных обязательных проверок PR сливается со свёрткой коммитов.
- Если человек явно не запретил публикацию, агент самостоятельно выполняет
  полный цикл: push ветки → PR → проверки → squash merge → синхронизация
  локального `main` → удаление рабочей ветки локально и в `origin`.
- Стабильный тег `vX.Y.Z` и необязательный `vX.Y.Z-rc.N` создаются только
  отдельной задачей человека по `docs/OPERATIONS.md`.

## Что можно менять

- `BACKLOG.md` и сгенерированную из него `.tasks/`;
- `COMPOSITION.md` — состав, назначение и границы заданных человеком
  репозиториев;
- `CONVENTIONS.md` — общие контракты и event envelope;
- системный `docker-compose.yml`;
- `adr/`, README и правила хаба;
- CI и evidence, необходимые для обязательной проверки.

## Ограничения

- Агент не создаёт и не удаляет репозитории, не меняет их назначение и не
  переносит высокоуровневую ответственность без явного решения человека.
- Код сервисов, интерфейсов и автономных компонентов, их `Dockerfile`,
  архитектурные документы и локальные backlog хранятся в соответствующих
  репозиториях.
- Сервисы взаимодействуют через брокер. Интерфейс может обращаться к сервису по
  HTTP/WS; stub-цель наблюдается out-of-band.
- Нельзя коммитить `.env`, секреты и lock-файлы без явного разрешения.
- Все диаграммы оформляются только блоками Mermaid.
- Нельзя ослаблять обязательный гейт, понижать риск, принимать остаточный риск
  или расширять собственную автономность.

## Версионирование контрактов

- `CONVENTIONS.md` экспонирует версии `CONVENTIONS@v1`, `@v2` и далее.
- Сервисы закрепляют потребляемую версию; проверка совместимости выполняется
  против этого пина.
- Выпущенная версия `@vN` неизменна. Несовместимое изменение создаёт
  `@vN+1` отдельным PR, после чего сервисы мигрируют своими задачами и PR.
- Stub-целям `CONVENTIONS@vN` неприменим, если они не потребляют envelope.

## ADR

- ADR хранится в `adr/NNNN-kebab-case.md`; нумерация сквозная.
- Обязательные разделы: `Status`, `Scope`, `Context`, `Decision`,
  `Consequences`, `Alternatives considered`, `Related`.
- `Scope` — `Сквозное` или список затронутых репозиториев.
- Допустимые статусы: `Accepted`, `Proposed`, `Superseded`, `Amended`.
- Старые решения не удаляются, а помечаются заменёнными. Индекс находится в
  `adr/README.md`, шаблон — в `adr/_TEMPLATE.md`.

## Нейминг, README и лицензии

- Репозитории называются `cybercity-<slice>`; хаб — `cybercity`.
- Идентификаторы сущностей и топологии используют kebab-case.

## Проверка и коммиты

Перед коммитом запускается закреплённый verifier методологии. Недоступность
обязательной проверки не считается успехом.

Коммиты используют Conventional Commits. Допустимые области:
`composition`, `conventions`, `deploy`, `adr`, `docs`.

Документация и тело коммита — русские; идентификаторы и краткое описание
коммита могут быть английскими. Несовместимость отмечается
`BREAKING CHANGE:` в теле.
